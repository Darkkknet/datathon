# CQA — Conversation Quality Analytics (Freedom Broker hackathon)

Прототип оценки работы оператора в чатах и звонках (RU / KZ / EN) по настраиваемому чек-листу,
с апелляцией и пересмотром. Задание: `docs/task_guide.pdf`, чек-лист: `docs/checklist.pdf`.

**Перед любой задачей прочитай этот файл и `docs/contracts.md`.** Контракты — единственный источник
правды о форматах данных. Если задача требует изменить контракт — остановись и скажи об этом,
не меняй его сам.

## Стек
- Backend: Node.js 20+, **без внешних зависимостей** (node:http, fetch). Хранилище — `storage/db.json`.
  Не добавляй npm-пакеты без крайней нужды: команда не программирует, запуск должен быть «поставил Node — запустил».
- Frontend: чистый HTML/CSS/JS, Web Components (без фреймворков и сборки) — чтобы потом встроить
  как HTML-компонент Dynamics 365
- LLM: `claude-sonnet-5-5` (основная), `claude-haiku-5-5` (дешёвый режим). Модель в `.env`. Без ключа — MOCK-режим.

## Жёсткие правила
1. **Итог считает только код** (`server/scoring.js`). LLM возвращает ответ/ступень, обоснование и ID реплик — никаких баллов.
2. **Чек-лист не хардкодится.** Промпт собирается из текущей версии чек-листа. Новый/заменённый критерий
   должен работать без правки кода — это проверят на защите.
3. Каждое сохранение чек-листа = новая версия. Оценка ссылается на `checklist_version`. Старые оценки не перезаписываются.
4. Реплики нумеруются по индексу в `transcript` (0-based). Исходные `timestamp` не меняем.
5. Реплики `bot` и `system` — контекст, оценивается только `operator`.
6. Ключи только в `.env` (в git — `.env.example`). Не логируй транскрипты целиком в консоль.
7. Тексты интерфейса на русском. Обоснования LLM — на русском, цитаты — на языке оригинала.
8. После правок: `npm test` и ручная проверка в браузере.

> Команда без опыта программирования: код пишет Claude. Объясняй изменения простыми словами,
> давай команды целиком, которые можно скопировать.

## Промпты для агентов (субагентов)

Запускать как отдельного агента (в своей ветке / worktree), когда основная работа идёт параллельно.
Каждому агенту контекст с нуля — промпты самодостаточные.

### 1. Тестировщик расчёта итога
```
Прочитай CLAUDE.md, docs/contracts.md (раздел «Расчёт итога») и config/checklist_v1.json.
Ты НЕ автор server/scoring.js — проверь его независимо.
Напиши tests/scoring.test.js с граничными случаями:
- все критерии «Да» → 100.00
- N/A у c03 и c07 → вес перераспределён, максимум 100
- шкала: c04=15 → 15/20 веса, c06=7 → 0.7 веса
- все весовые критерии N/A → total = null
- c08 = Да → total не меняется, critical_error = true
- N/A на критерии с na_allowed=false → ошибка валидации
- ступень не из шкалы → ошибка валидации
- округление до 2 знаков (пример: 65.5/75*100 = 87.33)
- новый критерий с произвольным весом и шкалой 0–5 считается без правки кода
Запусти тесты. Если тест падает из-за бага — опиши баг и минимальный фикс, но scoring.js не меняй.
```

### 2. Прогон по DEV и отчёт о расхождениях
```
Прочитай CLAUDE.md и docs/contracts.md.
Запусти `npm run eval:dev` (или POST /api/evaluations/batch для всех 65 диалогов DEV).
Сравни с ручной разметкой в fixtures/gold.json (если есть).
Сделай отчёт reports/dev_eval.md:
- доля совпадений по каждому критерию, отдельно по языкам RU/KZ/EN и по каналам (чат/звонок)
- список расхождений: conversation_id, критерий, модель vs эталон, цитата
- невалидные JSON / ретраи / ошибки API
- средняя стоимость и время одной оценки (по usage)
- 3–5 конкретных правок промпта server/llm/prompts/*, которые закроют самые частые ошибки
Промпт сам не меняй — только предложи.
```
